# Flow Error

Flow Error 将生产自动运行的失败上下文交给另一个 Flow，可用来发送通知、记录事故或执行自定义处理。

## 配置

1. 创建错误处理 Flow，在根图添加 **Flow Error**，连接处理节点。
2. 在 Flow Error 属性面板的 **监听的上游工作流** 中搜索并勾选一个或多个已发布 Flow。
3. 发布并启用当前错误处理 Flow，保持 Flow Error 未暂停，监听关系即生效。无需修改或重新发布上游 Flow。

不能选择当前 Flow、未发布或已删除的 Flow。已发布但暂停运行的上游可以选择，恢复自动运行后即可监听。每个 Flow Error 可以监听多个上游，同一个上游也可以被多个错误处理 Flow 监听。

监听列表保存在 Flow Error 节点的 `sourceFlowIds`，随草稿保存，支持撤销和重做；历史发布版本只读。所选上游后来不可用时保留选择并提示，可以取消选择；发布时再次验证上游资格。空列表表示不监听任何 Flow。

## 关联与生效时机

发布错误处理 Flow 时，在同一事务内更新该 Flow 的线上监听索引 `error_subscriptions`。未发布的草稿修改不影响线上监听。删除 Flow Error 并重新发布会清除监听关系。

源运行失败时查询当时已发布、已启用且未暂停的监听者，为每个处理 Flow 保存一条待派发记录。派发时再次验证该监听关系和处理 Flow 的可用状态；关系已移除则记录启动失败。目标版本在派发准入时固定为当前 Live。

## 触发规则

只有 Webhook、Schedule、Poll 等生产自动触发的运行，在最终失败或结果无法确认（`indeterminate`）时才派发。手动 Draft 和 Live 运行、成功运行、取消运行都不会触发。

每个失败运行对每个监听它的错误处理 Flow 至多创建一个处理运行。队列满时等待容量恢复，服务重启后继续派发。目标在派发时不可用会记录错误处理启动失败。错误处理运行再次失败不会继续触发其他错误处理 Flow，即使两个 Flow 互相配置，也不会形成循环。

原运行始终保留失败状态；错误处理成功不等于原运行重试成功。`indeterminate` 表示执行结果无法确认，可能已经发生外部副作用，不能据此直接判断可以安全重试。

## 输出与测试

Flow Error 提供三个对象输出：

- `workflow`：源 Flow 名称、ID、固定 Revision 和 Publication。
- `execution`：源 Run ID、终态、开始与结束时间。
- `error`：错误码、消息，以及可取得的失败节点、执行 ID 和 Subflow 调用路径。

在错误处理 Flow 的运行菜单选择 Flow Error，可用预填的样例数据手动测试下游分支。此操作不会伪造生产失败，也不会再次派发错误处理。

源运行详情显示等待派发、已创建处理运行或无法启动；已创建时可跳转至处理运行。处理运行详情可以返回源运行。
