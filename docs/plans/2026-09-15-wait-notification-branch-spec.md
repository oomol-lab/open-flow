# 等待节点通知出口与局部等待

状态：已实施并完成本地自动化与 Lab 验证；产品页完整验收和部署升级尚未完成。2026-09-15。

已确认的方向：等待节点增加可连线的通知出口，移除内联通知配置；通知出口之后按普通图规则执行，没有通知专属时限，用户批准、拒绝或继续后也不取消该分支。
核心语义：**Wait 只阻塞尚未决议的操作出口，其他具备执行条件的节点继续执行。**

本文定义产品行为与实施边界。实现和权威合同已同步，具体证据与剩余验收项见实施计划；本文不代表已部署上线。
参考：[架构](../architecture.md)、[Control API](../control/contracts/control-api.md)、[版本演进](../control/contracts/compatibility.md)。

实施安排见[等待节点通知出口与局部等待实施计划](2026-09-15-wait-notification-branch-plan.md)。

## 1. 目标与范围

等待节点负责创建可决议的等待、提供提示与操作链接，并在收到决议后释放对应出口。
通知出口后的节点可以发送消息、创建待办、更新状态或执行业务；这些节点属于原 Run 的普通执行图。
“通知分支”只用于描述连线位置，不定义独立执行范围、预算、故障域、调度器或恢复协议。

本次包含：

- 普通 Wait 的通知出口、输出 schema、端口就绪与数据来源检查。
- Wait 的局部阻塞，以及同一 Run 内执行与等待并存的调度语义。
- 执行期间持久化决议、多个独立等待、整体暂停与恢复。
- 公共模型、Server、Control API、Command、Workbench 与 Lab 的一致支持。
- 删除普通 Wait 内联通知配置及其专用编辑流程。

Agent 不增加通知出口，保留现有内联审批通知配置与发送能力。
Agent 的待审批状态接入统一的局部等待、独立决议与 Run 暂停机制；同一个 Agent 内部仍按既有工具批次与审批规则推进。
普通 Wait 和 Agent 的节点放置规则保持既有边界，本次不扩展 Subflow 内的暂停能力。

## 2. 用户行为

```text
                  ┌ 通知 ──→ 发送邮件 ──→ 写入通知记录
上游 ──→ 等待节点 ├ 批准 ──→ 执行业务
                  └ 拒绝 ──→ 记录拒绝
```

1. 到达 Wait，先保存等待记录，再释放通知出口，开始发送邮件。
2. 用户可以在其他节点仍执行时批准或拒绝。
3. 批准后，“执行业务”在依赖满足、资源可用时启动，“写入通知记录”继续执行。
4. Run 在所有应执行工作结束且没有未解决等待时完成。

继续模式提供“通知”和“继续”两个出口，遵循相同规则。
用户先于通知节点启动完成决议，也不会跳过通知节点。只要 Run 仍可执行，该节点就按普通依赖规则运行。
因此，消息可能在决议后才送达；链接应返回已有决议事实，不能再次执行操作。

| 事件                         | 行为                                                      |
| ---------------------------- | --------------------------------------------------------- |
| 通知节点完成                 | 继续调度其下游，未决议 Wait 仍等待用户。                  |
| 用户完成等待操作             | 释放所选操作出口，其他分支保持运行或待调度状态。          |
| 通知节点失败                 | 按普通节点失败规则处理，可能结束整个 Run 并中断其他分支。 |
| 操作出口后的节点完成         | 如其他分支或等待未结束，Run 继续存在。                    |
| 普通节点超时、Run 超时或取消 | 沿用统一失败与取消机制，通知节点同样受影响。              |

批准已经被接受，不代表后续业务一定成功；通知或业务节点随后失败时，Run 仍可能失败。已完成的外部效果不回滚。
本次不增加通知专属的“忽略失败”、自动重试或取消豁免。未来需要容错时，通过普通节点的错误处理合同表达。

## 3. 节点与输出合同

### 3.1 配置

- 所有普通 Wait 固定提供 `notification` 出口，显示名称为“通知”。没有连线时，不启动通知后续节点。
- `actions` 仅包含 `continue` 或 `approve/reject`。`notification` 不是用户 action，resolve API 必须拒绝它。
- 保留标题、描述、提示、等待方式和输入配置；原有操作出口继续输出该 Wait 接收到的值。
- 删除 Wait 的 `notification` 配置对象，包括 Task 引用、消息字段和通知输入映射。
- 删除内联应用选择、参数与账号配置；后续 Connector 节点自行配置这些内容。
- 不新增通知超时字段、独立预算或行为开关。

切换等待方式时保留通知连线。复制、删除、撤销、重做、导入导出及依赖闭包计算同步支持新端口，并清理不再被使用的旧内联通知 Task。
仍被其他节点或 Agent 引用的 Task 必须保留。

### 3.2 通知数据

`notification` 输出一个 JSON 对象，类型由公共 Flow 层定义；`value` 沿用 Wait 输入的 JSON Schema 与 nullable 约束。

```json
{
  "value": { "requestId": "request-123" },
  "prompt": "请确认是否发送这封邮件",
  "actions": [
    { "action": "approve", "url": "https://example.com/v1/wait-actions/<capability>/approve" },
    { "action": "reject", "url": "https://example.com/v1/wait-actions/<capability>/reject" }
  ],
  "expiresAt": "2026-09-22T08:00:00.000Z"
}
```

| 字段        | 合同                                                    |
| ----------- | ------------------------------------------------------- |
| `value`     | 此次 Wait 的输入值，与操作出口输出的值相同。            |
| `prompt`    | 固定 Revision 中的等待提示。                            |
| `actions`   | 按 Wait action 顺序提供操作名与完整 URL。               |
| `expiresAt` | 等待过期时间，使用 ISO 时间字符串，与普通执行预算独立。 |

不固定拼接消息正文，不新增表达式系统；文本或卡片由后续节点通过现有能力组织。
普通 Wait 不因通知出口是否连线而增加 Run/Publish 的公开 origin 预检。完整操作链接由 Server 的等待创建逻辑使用部署对外地址生成。
实际需要生成链接却没有可用地址时，按普通执行配置错误处理，不返回缺失或无效 URL，也不改变输出 schema。未连接也未引用通知出口时不必生成公开 capability。连接通知执行边，或在普通输入映射中引用通知输出，均需要生成完整通知输出。
本项调整仅针对普通 Wait，Agent 内联通知的既有部署能力检查保持不变。
Connector 等能力检查由实际节点决定，不因使用通知出口而额外要求 Connector。

### 3.3 输出分两个阶段产生

| 阶段                 | 端口状态                                           | Wait 节点状态 |
| -------------------- | -------------------------------------------------- | ------------- |
| 等待创建成功         | `notification` 可用；操作出口尚未确定。            | 等待决议。    |
| 合法决议被接受并应用 | 通知输出保留；所选操作出口可用，其余操作出口关闭。 | 完成。        |

通知输出只产生一次。决议不会清空它、重发它，或再次调度已经执行过的通知后续节点。
Wait 的完成事件只在应用决议后产生一次；通知输出就绪不能伪装成 Wait 已完成。
到达 Wait 前尚未满足依赖时，以及整个 Wait 被上游分支跳过时，都不能产生通知输出或等待记录。

这项分阶段输出行为限定在 Wait 合同内。普通 Task 继续在完成时一次性发布输出，不引入通用流式端口或任意节点提前提交结果接口。

## 4. 依赖与分支汇合

调度器需要区分端口的“尚未确定”“已有值”和“已关闭”状态。
仅依赖通知出口的节点不能被 Wait 尚未完成阻塞；操作出口也不能因暂时没有值而提前视为已跳过。

通知出口后允许普通分叉、汇合、结果引用，以及在现有节点放置规则允许位置连接其他 Wait 或需要审批的 Agent。
不划分独占的通知子图，不禁止它与操作出口后的路径汇合，也不禁止不同 Wait 的后续路径共享节点。

汇合遵循现有图规则：所有入边必须已确定，且至少一条入边被选中，才可能执行目标节点；输入映射还必须满足既有可用性与类型规则。
因此，同时连接通知边和操作边的节点必须等该操作边被选中或关闭；不能因通知边先就绪就提前运行。
普通汇合不自动表示“所有入边均被选中”，需要仅在批准路径执行的逻辑仍须正确表达分支与数据依赖。

公共静态检查必须处理以下区别：

- `notification` 与 `approve` 可以先后产生，并非互斥；`approve` 与 `reject` 仍然互斥。
- 通知后续路径不能仅凭祖先关系直接读取尚未产生的操作输出；必须存在保证该值可用的执行依赖。
- 操作后续路径引用通知处理结果时，同样必须等待对应生产节点；引用本身不能成为绕过执行图的隐式等待机制。
- 通知与操作输出可能同时存在，不能把二者配置为“互斥来源”而绕过一个输入恰好一个可用来源的要求。
- 分支汇合后的节点每次 Run 只执行一次，不因同一 Wait 后续又产生操作输出而再次执行。
- 环、不可满足的数据引用、无法确定的依赖继续明确报错。

这些规则由公共图分析拥有，覆盖 API、Command、导入和 Workbench。前端不能维护另一套合法连线定义。

## 5. 执行与等待并存

### 5.1 到达 Wait

1. Scheduler 解析 Wait 输入，分配稳定的等待身份，请求 Run owner 创建等待。
2. Run owner 持久化该 Wait 的输入、提示、action、过期时间与 capability 验证信息，并绑定固定 Run/Revision/节点身份。
3. 提交成功后，该等待立即可被查看和决议；Scheduler 取得通知输出并释放通知出口。
4. 其他具备执行条件的节点继续执行，不因创建等待而全局停止调度。

创建等待时无需等待无关的运行中节点结束，也不要求此刻已经具备可安全恢复的完整图 checkpoint。
等待记录和整图恢复快照承担不同职责：前者保证决议事实可靠，后者只在安全暂停边界保证恢复。
等待创建失败时不得发布可用链接或执行依赖该输出的节点；错误按 Run 持久化失败语义处理。

### 5.2 执行与恢复期间收到决议

所有入口统一执行同一个 first-writer-wins 决议操作。身份是 `runId + waitId`，不能只以节点 ID 或 Run 当前摘要定位。

- Run 处于 `running`、`waiting`、`queued` 或 `starting`，目标 Wait 已创建且未过期时，均可接受合法决议。
- 先原子持久化决议，再唤醒持有该 Run 的 Scheduler；唤醒是提示，权威记录才是事实。
- 正在执行的 Run 在原 session 应用决议，释放对应出口；不得另建一个并发恢复 session。
- 已安全暂停的 Run 进入队列，按正常资源与同 Flow 串行约束恢复。
- Run 已处于 `queued` 时，继续保存其他等待的决议，不重复排队；处于 `starting` 时交由已经领取该 Run 的唯一执行者应用，不另建 session。
- 恢复执行者必须读取并接续处理领取前后新接受的决议，不能仅使用 claim 时捕获的快照。启动期间的决议不得丢失或要求用户重试。
- 重复或竞争提交沿用现有返回语义，不重复完成节点，也不重跑后续节点。
- 接受决议不会取消通知节点、其他等待或任何无关分支。

用户在通知输出交付给 Scheduler 前就完成决议时，仍要按序发布本次通知输出并应用决议，不能丢掉通知路径。
Run 终态、过期与决议竞争由 Run owner 仲裁；终态不能被迟到的决议或节点回调重新激活。

### 5.3 多个等待

同一 Run 可以存在多个已到达、未解决的等待。它们分别可见、可决议、独立过期；不再把普通独立等待收敛成单个可操作项和不可操作队列。
解决其中一个只推进它所控制的出口，不要求先解决更早或更小节点 ID 的等待。

Agent 内部尚未轮到的工具审批不算已到达的等待，仍由该 Agent 的串行工具合同决定何时创建。
不同 Agent 或 Wait 已创建的等待则共享以上独立决议规则。Agent 内联通知只负责自身等待的消息发送，不成为全图串行审批的理由。

未解决等待的过期沿用既有 Wait 过期导致 Run 失败的规则，在 `running`、`waiting`、`queued` 和 `starting` 期间均须生效。
过期结束 Run 后，排队或已领取但尚未开始执行的工作不能再启动；已活动的执行按统一终态规则停止。
已经解决的等待保留历史决议，之后的其他等待或 Run 终态不得覆盖它。

## 6. Run 状态、预算与完成

### 6.1 两分钟内存等待窗口

整个图没有运行中或可执行工作、仍有未解决等待时，开始固定 **120,000 ms（两分钟）** 的内存等待窗口。
窗口内不序列化或保存完整 checkpoint，保留当前 session、执行槽与同 Flow 执行所有权；Run 保持 `running`，节点仍显示等待用户。
等待记录和用户决议继续在发生时立即持久化，不随窗口延后。

- 两分钟内有效决议使图可以推进时，取消窗口并在原 session 继续，不保存完整 checkpoint。
- 再次执行到图静止时，重新开始两分钟窗口；重复决议、查询和无效唤醒不能延长当前窗口。
- 窗口到期时重新读取决议并检查图状态；仍然静止才生成、验证和提交 checkpoint，成功后进入 `waiting` 并释放资源。
- Run 取消或未解决等待过期时立即按统一终态规则结束，不等满窗口。
- 窗口是统一 Run 暂停策略，适用于普通 Wait 和 Agent 审批，不是通知分支时限，也不提供用户配置项。

### 6.2 Run 状态与资源

节点等待与 Run 暂停是两个独立事实：

| Run 情况                                             | Run 行为                                                                       |
| ---------------------------------------------------- | ------------------------------------------------------------------------------ |
| 执行 session 中还有可执行或运行中的节点              | 保持 `running`，可以同时存在待决议项。                                         |
| 无可执行、运行中的节点，但有未解决等待               | 先在内存中等待两分钟，到期仍静止才提交 checkpoint、进入 `waiting` 并释放资源。 |
| 暂停中的一个或多个等待已解决                         | 原子转为可恢复状态，进入 `queued`，由唯一执行者恢复。                          |
| 所有应执行节点已完成或按分支规则跳过，没有未解决等待 | 正常完成。                                                                     |
| 没有工作也没有等待，但仍有无法满足的依赖             | 明确失败，不能伪装成等待或成功。                                               |

通知节点与其他节点共用 Run 的执行预算、节点超时、能力边界与部署并发限制。
执行预算按实际执行段的墙钟时间累计，并行节点不重复计时；某个 Wait 未决议不意味着其他执行时间免费。
两分钟窗口内的纯内存等待、安全暂停与恢复排队均不消耗执行预算，继续执行或恢复不得重置预算。
计时须排除纯内存等待，不能让覆盖整个 session 的墙钟 timeout 在窗口期间继续扣减；通知或其他节点仍运行时照常计时。等待过期时间独立按实际时间推进。

普通失败、deadline、Run 取消、Flow 删除和服务关闭继续统一传播到整个活动执行范围。
不创建通知专属状态机、执行槽、并发池、租约或终止原因；通知节点的普通失败会按既有语义影响其他分支和 Run。
同 Flow 的执行串行规则保留；Run 只有真正暂停后才释放所占执行槽，不能因为某个节点在等待就假装整个 Run 已暂停。

## 7. 持久化、暂停与恢复

### 7.1 安全暂停边界

完整 checkpoint 必须覆盖恢复所需的固定输入、Variable 快照、已完成与跳过节点、Wait 已发布输出、未解决等待集合、已接受决议的应用状态、Agent continuation 和剩余预算。
节点输出与完成事实、Wait 出口发布与决议事实要能共同验证；不允许恢复时通过重新执行节点或重新生成等待来补齐缺失状态。

暂停提交与决议接受可能竞争。Run owner 必须保证：

- 不能用旧快照覆盖刚接受的决议。
- 暂停前未应用的已接受决议，在当前 session 或下一次恢复中应用且仅应用一次。
- 当决议已经使工作可执行时，不能把 Run 遗留在无唤醒的 `waiting` 状态。
- 同一个 Run 任意时刻只有一个 Scheduler 执行者；旧 session 的迟到回调不能修改新执行段。

运行中的决议传递、暂停提交和队列 claim 都从同一份权威事实协调，不依赖内存通知必达。

### 7.2 恢复与不确定执行

通知后续节点使用普通图恢复规则：已完成或已跳过节点不重跑，尚未执行且满足依赖的节点继续执行。
Wait 的通知输出不会因恢复再次发布；操作出口仅按该 Wait 已保存的合法决议释放。

安全暂停后重启，恢复同一 Run 的完整图状态与所有等待。运行期间或两分钟内存等待窗口内进程崩溃而无法证明安全续接时，按现有 Run 不确定恢复规则终止，不能从更早快照猜测性重放外部效果。
持久化了等待或决议不等于已经持久化整个运行中执行段；即使决议已被接受，也不能因此承诺崩溃后一定可恢复业务执行。

不增加通知独有的“重启后放弃”“最多启动一次后台任务”或整分支自动重试协议。
普通节点执行身份、幂等约束、结果验证与外部调用不确定性规则继续生效。

### 7.3 通知数据与凭据恢复

通知输出可以被普通下游节点在后续恢复段引用，必须像其他输出一样保持稳定，不得重新生成 capability 或因脱敏改变作者实际收到的值。
公共 origin 仍属于部署配置，不进入 Revision；已经生成的运行时 URL 随该次输出固定。

capability 的公开验证索引只保存不可逆摘要。作为图输出的完整 URL 则可能进入受保护的 Run value 与恢复快照，这是支持普通数据依赖所需的运行数据，必须明确更新现有凭据持久化合同。
这些数据受 Run 读取权限、存储保护与清理规则约束，不进入 Revision、匿名接口、公共诊断或部署日志。
不能一边禁止保存恢复所需的输出，一边承诺普通图恢复；具体编码与存储访问规则在公共合同和 Server 实施阶段一起固定。

## 8. 所有权与现有实现调整

Scheduler 拥有图依赖、端口就绪、节点运行与决议应用；Run owner 拥有等待事实、持久化、决议仲裁、队列和执行 session 的唯一性。
执行器、Task 与 Connector 调用继续沿用现有监督和 Effect interruption，不增加脱离 Run 生命周期的后台 Promise。

现有实现中，下列行为需要直接替换：

- 遇到 Wait 后用全局 `suspending` 阻止其他节点启动。
- 等待所有活动节点结束后才创建可决议的 Wait。
- checkpoint 只表达一个当前可决议 Wait 及后续排队等待。
- 只允许 `status == waiting` 的 Run 接受操作。
- 收到每个决议都通过新 session 从 checkpoint 恢复。
- 将 Wait 当作只会在完成时选中一个输出的普通互斥分支节点。

复用既有运行记录、持久化和调度设施，实现统一的局部等待，不为通知另建执行体系。
Agent 的配置与外部通知机制保留，但上述全局暂停和单一当前等待假设不能留在共享路径中。

## 9. Workbench、API 与运行记录

### 9.1 编辑态

- 固定显示通知出口，使用现有画布端口与分支样式，支持两种等待模式。
- 配置说明：“进入等待时执行通知出口后的节点；完成等待操作后，对应出口继续执行。”
- 输入选择器识别通知对象，图分析负责类型、时序、汇合与来源诊断。
- 删除普通 Wait 内联通知应用、参数、消息字段和账号界面及专用文案、样式。
- 不显示通知专属倒计时，不提示批准会中断通知，也不因通知路径位置隐藏合法节点类型。
- 相关语言、复制粘贴和变更历史同步覆盖。

### 9.2 运行态与公共接口

Run detail 提供当前未解决等待集合，不再把单个 `waiting` 对象限定在 `status: waiting` 下。
集合中的每个等待都有独立的 `waitId`、节点归属、action、提示与过期信息，沿用明确的鉴权与字段访问规则。
存在未解决等待的 `running` Run 也必须被“待处理”查询发现；筛选条件不能只等于 Run 的暂停状态。
精确响应字段、事件名称和筛选参数在 API 合同阶段固定，并贯通严格 decoder、客户端、Command 与 MCP。

Workbench 同时显示整体运行状态、各节点状态和可操作等待列表。可以显示“运行中 · 2 项待处理”，不能把所有节点画成暂停。
用户可分别处理等待；决议按钮不因其他节点执行而禁用。已接受决议与后续业务执行结果分别表达。

等待创建、决议、节点完成以及整图暂停是不同事件。不能在每次创建局部等待时发送表示整个 Run 已暂停的事件。
复用普通节点日志、输出和失败展示，不引入通知专用历史或进度数据源。Wait 发布通知后仍显示等待，应用决议后才显示节点完成。

Lab 并排覆盖审批与继续模式、无通知连线、通知运行期间批准、两条路径并行、分支汇合、多个待处理项和普通失败状态。
使用真实组件与确定性数据；保留 Agent 内联审批通知配置与运行覆盖。

## 10. 版本与已有数据

本次同时修改模型、Engine 运行语义、Scheduler checkpoint 和 Control API。按现有版本演进规则声明断点及拒绝路径，并同步更新受影响版本和分发产物。
旧 Wait 内联通知字段不能被当作普通未知字段静默丢弃；旧的单等待 checkpoint 也不能按新合同猜测解释。

- 不在读取旧 Revision 时修改内容、重算 digest 或隐式生成后续通知节点。
- 使用旧 Wait 通知合同的数据需要明确诊断，通过可审核迁移或重新编辑创建新 Revision。
- 旧活动 Run 在升级前完成或取消，或由明确保留的旧 Engine 环境恢复；不让新旧 Scheduler 同时拥有一个 Run。
- 实施前盘点真实旧数据，判断是否需要一次性迁移工具；不为了假设中的兼容保留运行时包装层。
- 删除旧 Wait 的通知 Task 引用与专用发送路径时，保留 Agent 仍使用的共享能力。

architecture、Control API、版本演进、运行事件和 Command authoring 合同已随实现同步更新。旧部署数据的盘点和升级仍是发布前条件。

## 11. 实施顺序

1. 固定 Wait 两阶段输出、端口就绪、汇合与输入来源规则，以及多等待和版本边界。
2. 用确定性 Scheduler 测试验证通知持续执行时接受批准、并行推进与正确收敛；替换全局暂停假设。
3. 实现 Run owner 的独立等待记录、运行中决议传递、唯一执行者及安全暂停竞争处理。
4. 更新 checkpoint、恢复验证、剩余预算与受保护通知输出持久化，覆盖崩溃和迟到回调。
5. 贯通 API/Command/MCP 的多等待查询与决议、运行事件和 Workbench 展示。
6. 删除普通 Wait 内联配置，更新 Lab、公共一致性测试、分发合同和已有数据处理。

## 12. 验收标准

### 12.1 核心行为

- 通知节点保持运行时批准，批准出口后的节点能够开始，通知节点未收到取消且能继续推进下游。
- 在正常 Run 预算允许的前提下，通知路径超过 5 分钟仍能执行，不存在通知专属截止时间。
- 通知尚未被调度时接受决议，通知与所选操作路径都正常执行，未选操作路径被跳过。
- 图静止后使用可控时钟验证 120,000 ms 窗口：到期前没有完整 checkpoint 序列化或写入，到期仍静止才保存并释放；通知或其他节点仍运行时不启动窗口。
- 窗口内批准后原 session 继续且没有 checkpoint 写入；再次静止重新计时，重复决议与无效唤醒不延长窗口。
- 覆盖窗口到期与决议竞争、窗口中取消或等待过期，不能丢决议、双启动或等满窗口才取消。
- 操作路径结束但通知路径尚未结束时，Run 不提前完成。
- 通知节点失败或超时时，沿用普通失败与取消规则，即使用户已批准也不隐藏失败。
- 全局取消和 Run deadline 覆盖所有活动节点，保持已有外部调用不确定性语义。

### 12.2 图与多个等待

- 通知出口与操作出口可以先后产生，审批的两个操作出口仍互斥；通知输出就绪不提前完成 Wait。
- 通知与操作路径可按普通规则汇合，目标节点等依赖确定后只运行一次。
- 输入来源检查拒绝没有保证就绪的未来值，以及把通知与操作输出误当互斥来源的映射。
- 通知路径后可以连接另一个根图 Wait，两个已到达等待均可独立处理，后到达者不被强制排队。
- 两个独立 Wait 按任意顺序决议，只推进各自出口；可汇合时按图规则收敛。
- Agent 审批不阻塞无关图节点；多个 Agent 与普通 Wait 的已创建等待可以独立处理，Agent 内部工具顺序不变。
- 无通知连线、Wait 被上游跳过、条件路径关闭和部分路径已解决等情况正确收敛。

### 12.3 持久化与竞争

- 等待先持久化，再发布通知输出；失败时不产生依赖该输出的外部效果。
- 每种决议入口均可处理 `running`、`waiting`、`queued` 和 `starting` Run 的有效等待，重复和竞争提交只应用一次。
- 同一 Run 的第一个决议使其进入 `queued`，因资源或同 Flow 串行限制尚未恢复时，第二个决议仍被接受；再覆盖 `starting` 期间提交第二个决议，恢复后全部恰好应用一次且只有一个 Scheduler。
- 决议与通知输出交付、暂停提交、队列 claim、节点失败及 Run 取消竞争，不丢决议、不双启动、不复活终态。
- 丢失内存唤醒后仍能从权威状态推进，旧 session 回调不能污染恢复段。
- 安全暂停后重启，已完成通知节点不重跑，尚未执行的合法后续节点继续运行，输出与链接稳定。
- 多个等待、已发布通知输出、未应用决议及 Agent continuation 均能被 checkpoint 正确恢复与验证。
- 运行中崩溃且无法证明安全续接时，不从旧快照重放外部效果；已保存决议事实仍可查询。
- 执行预算跨段累计，并行不重复扣减；两分钟内存等待、安全暂停与恢复排队不扣减，继续或恢复不重置预算。
- 内存等待窗口中模拟进程崩溃，不能仅凭已持久化的等待或决议重放旧执行段；没有安全恢复点时明确结束为结果不确定。
- 未解决等待在 `queued` 与 `starting` 期间过期时同样结束 Run，已领取执行不得启动或复活它；已决议等待不会随后因旧过期任务错误结束 Run。

### 12.4 编辑、产品与检查

- 新端口、输出 schema、编码往返、变更操作、复制和撤销重做一致，旧内联字段有明确拒绝或显式迁移结果。
- 普通 Wait 缺少公开 origin 时不被 Run/Publish 提前拒绝；实际生成链接时明确报告配置错误，无无效输出或依赖该输出的副作用。未连接也未引用通知出口时可通过管理入口完成等待；Agent 原有检查继续生效。
- 运行详情与待处理查询包含运行中的待决议项；多个等待可以分别操作。
- Lab 检查端口、配置简化和并行状态，实际产品页验证发起等待、提前决议、继续执行和最终汇合。
- 以受控 Task、Connector、时钟和执行器 fixture 验证行为，不依赖真实发信或其他外部写操作。
- 运行受影响模块测试、公共一致性检查和必要的分发验证；提交前从仓库根目录通过 `bun run check`。
