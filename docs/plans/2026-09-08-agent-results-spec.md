# Agent 大工具结果处理

状态：已实现主链路、公共读取接口和客户端入口。本文细化 Agent spec 的工具结果处理，取代其中将超过 1 MiB 的已成功工具结果直接终止的设计。

## 1. 问题与目标

当前 `apps/server/node/deployment/connector.ts` 在读取响应时限制 1 MiB；`deployment/agent.ts` 又将超过 1 MiB 的工具结果视为致命错误，并把完整结果写入模型工具消息和运行日志。框架 continuation 会继续携带消息，因此简单放宽下载限制仍会造成上下文、日志或 checkpoint 超限。

目标行为：Connector 调用成功后，完整结果可靠保存；模型获得有明确完整性标记的预览，需要更多数据时读取已经保存的结果；用户能够查看和下载完整结果。正常的大结果不导致业务工具重试或 Run 失败。

本次不实现通用文件系统、跨 Run 搜索、模型生成代码或自动摘要模型。结果读取能力仅用于本 Agent invocation 已取得的数据，不新增外部应用权限。

## 2. 当前实现约束

- `RunStore.append` 会因单条事件、事件总量或数量超限而放弃日志；事件还会独立过期。日志不能作为结果存储或恢复依据。
- Server 尚无可复用的 Artifact 持久化实现。不能只保存一个临时文件路径或依赖进程内 Map。
- Agent 的框架快照和 Scheduler checkpoint 在审批暂停时由 Run owner 原子提交，完整 checkpoint 上限为 16 MiB。
- Flow 删除由现有生命周期 owner 清理所有 Run 关联资源；新增结果必须进入同一路径。
- 当前部署模型配置没有可靠的 context window 和 tokenizer 元数据，不能声称按精确剩余 token 自适应。

## 3. 结果的所有权与持久化

Server 为 Agent 保存不可变的 Run result。每个结果关联 `runId`、`invocationId`、`callId`、`toolId`、Action、规范化输入摘要、结果 digest、UTF-8 字节数和创建时间。

`resultId` 由宿主生成，不能用模型传入的路径作为存储位置。结果正文是完整 JSON，不做摘要或截断。结果 ID 不是访问凭据。

首版使用独立 SQLite 表保存元数据和 JSON 正文，避免新增文件与数据库之间的提交、清理协调。按 `(runId, invocationId, callId)` 保持调用身份唯一；正文大小和单 Run 总量在同一事务中检查。保留未来更换存储实现的模块边界，不提前增加通用存储抽象或后端配置。

成功路径顺序：

1. 接收完整响应，验证 Connector 成功 envelope 及 JSON 数据。
2. 使用原调用身份保存完整结果；写入成功后才向模型宣布成功。
3. 生成结果描述和有限预览，将描述写入日志并返回模型。
4. 后续审批 checkpoint 仅携带结果引用及有限预览，不复制完整正文。

已收到成功结果但存储失败，记录“调用已成功、结果保存失败”，停止 Run，不把错误交给模型重试。若外部调用与本地保存之间进程崩溃，继续遵守现有不确定恢复策略；结果存储不承诺外部 exactly-once。

同一已保存调用的受支持恢复路径必须校验 Action、输入摘要和结果 digest；不一致或引用缺失时失败，不重新调用 Connector 补数据。不将此机制扩展为任意失败 Run 的自动恢复。

结果跟随 Run 保留到 Flow 删除，不受日志 retention 或日志截断影响。当前不增加独立结果过期策略，以免审批等待恢复或运行检查失去正文。

## 4. 模型结果与按需读取

所有业务工具使用一致的宿主结果 envelope，包含结果引用、字节数、预览和明确的完整性信息。业务 JSON 放在 `value` 内，业务自身名为 `resultId`、`complete` 等的字段不会被解释为宿主控制字段。

小结果的预览包含完整 `value`。大结果的预览描述根类型、对象键或数组长度，并提供有界内容；未展示部分必须显式标记。不要截断 JSON 文本并冒充完整 JSON，不允许模型将省略字段视为字段不存在。

Agent 增加一个宿主提供的结果读取工具。它读取本次 invocation 的结果，不请求 Connector、不使用账号、不要求业务审批。名称由公共 Agent validation 预留，用户声明工具不能覆盖；固定为 `read_result`，已有同名配置报告明确冲突，不静默改名。

读取输入：`resultId`、JSON Pointer `pointer`（默认根）、`offset` 和 `limit`。宿主按实际数据类型解释分页：

- 对象：返回按保存时顺序分页的键及每个成员的有界预览。
- 数组：返回从 `offset` 开始的成员及各自 JSON Pointer。
- 字符串：按 Unicode code point 分段返回文本，说明这是原字符串的一部分。
- 数字、布尔、null：返回完整值。

读取输出包含 `pointer`、数据类型、总长度或成员数、当前 offset、实际返回数量、`nextOffset` 和完整性标记。单个成员超过预览预算时，返回该成员的类型、大小和可读取 pointer；不跳过成员，不返回无进展的同一游标。下一次可以深入该成员。

指针遵守 JSON Pointer 的 `~0`、`~1` 转义；只访问实际 own property，数组索引必须合法。不存在的路径、错误 offset 和跨 invocation 引用返回可纠正的读取错误，不能退回读取其他 Run 或整份正文。

结果读取仍消耗正常模型轮数，并遵守取消和节点总执行预算。审批恢复后重建读取工具，继续访问同一份已保存结果。

## 5. 预算与错误语义

分开设置三个预算，禁止共用一个 1 MiB 常量：

| 预算                   | 用途                             | 达到上限的行为                                                   |
| ---------------------- | -------------------------------- | ---------------------------------------------------------------- |
| Connector 响应资源上限 | 防止异常响应耗尽内存             | 中断响应，保留已知 HTTP 状态；业务结果未确认时仍为 indeterminate |
| 结果存储总量           | 限制单次响应和单 Run 存储占用    | 明确资源错误；已确认成功后不得声称未执行或重新调用               |
| 模型展示预算           | 限制预览和读取页进入上下文的体积 | 返回较小预览或下一页，不令业务工具失败                           |

实现起始值：动作响应 32 MiB，单 Run 结果正文累计 128 MiB，单条模型预览/读取页不超过 16 KiB。前两者是部署资源保护，后者只是展示策略；正常超过 16 KiB 的数据依然完整保存和可读。目录搜索、Proxy 等其他边界不随动作响应一起放宽。

这些数值不是 JSON Schema 或 Revision 的约束，不在每个 Agent 的 UI 增加大小配置。用真实响应和并发内存测试检查初始值，避免无依据地把它们当作模型上下文容量。

首版对工具消息中的预览维护总量预算：历史预览可缩减为结果引用，保留模型请求与工具响应配对、调用身份和结果可读性。系统指令、用户任务和审批事实不能因预览压缩而被删除。框架保存的消息也必须同步使用有界表示，不能只减少发送给 provider 的临时副本而让 checkpoint 继续增长。

当前没有可信模型窗口元数据，使用保守的预览总量策略并明确其不是 token 精确计算。总量初始预算为 128 KiB；最新读取内容优先保留，较早结果退回引用。最终 provider 上下文错误仍需明确报告，不能假称已完全避免。

不通过额外模型自动摘要原始结果，以免引入费用、信息损失和第二次模型调用失败。

## 6. 公共读取契约与界面

先在公共 Control API 定义严格解码的 Run result 描述和读取响应，再实现 Server、Workbench 和 Command 消费方：

- `GET /v1/runs/:runId/results`：分页列出结果描述，不返回完整正文。
- `GET /v1/runs/:runId/results/:resultId`：按 pointer 和 offset/limit 读取有界 JSON 页面。
- `GET /v1/runs/:runId/results/:resultId/content`：下载原始 JSON，使用附件响应，不渲染成可执行页面。

复用现有 Run 读取的认证与所属 Flow 检查；每次读取都同时验证 runId/resultId 关联。模型使用宿主绑定 invocation 的内部读取方法，不能通过公共 Operator API扩大自身可见范围。

日志只携带结果描述与有限预览，完整结果列表独立可读，因此日志被裁剪后用户仍能找到结果。Workbench 显示“执行成功 · 结果较大”，提供“查看结果”和“下载 JSON”。查看采用分页，首屏不下载整个结果，不将大 JSON 一次性挂入 DOM。

Command 使用相同公开契约，支持分页检查与下载；不 deep-import Server 存储或自行读取数据库。

技术参考在实现公共契约时记录精确类型、路由、分页上限和错误码。架构文档在存储实现落地时记录结果的 Run 所有权、读取授权和恢复不变量。

## 7. 实施顺序

1. 公共结果描述、分页与 JSON Pointer 行为及规格测试；预留宿主工具名。
2. Server 结果表、迁移、原子配额、调用身份、读取隔离和 Flow 删除清理。
3. Agent 成功写入结果、有界 envelope、`read_result`、日志引用及恢复校验。
4. 框架消息预览压缩，验证发送消息和保存快照同时有界；再放宽动作下载限制，移除旧 1 MiB Agent 致命判断。
5. Control API、Workbench 结果查看与下载、Command 入口。
6. 更新原 Agent spec、技术参考和架构边界，完成仓库检查与发布包检查。

不要先删除旧上限再补存储，也不要只放宽 Connector 响应而让 Agent 继续在下一层失败。

## 8. 验收

- 超过 1 MiB 的 Gmail 形状结果能完成工具调用；完整 JSON 下载后与原结果 digest 一致。
- 模型预览和读取页均有界且有效；单个巨大字符串、巨大数组成员、深层对象和多字节字符均可继续读取，无静默丢项。
- 错误 pointer、越界分页、工具名冲突及跨 Run/invocation 引用明确拒绝。
- 大结果之后进入审批，关闭并重开 Server 后继续读取旧结果，Connector 不会因此再次执行。
- 同批前一工具结果已保存、后一工具待审批时，拒绝或批准都保持调用顺序和结果身份。
- 日志截断或清理不影响结果和等待恢复；Flow 删除能够清理正文与元数据。
- 并发写入不能突破单 Run 配额；取消、磁盘写入失败、结果引用丢失和下载资源超限分别保持正确终态。
- 多轮读取时模型消息与 checkpoint 不随完整结果体积增长；验证消息配对和框架快照内容，不只验证请求体。
- UI 用仓库检查、交互测试和构建验证，不启动浏览器自动化。
