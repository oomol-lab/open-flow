# 飞书 Trigger 接入计划

状态：实施中。本文记录目标设计；未通过验证的项目不表示当前产品已经具备相应能力。

## 接入模型调整

事件源代表一个飞书应用的事件入口。创建时只选择 Connector 团队及已连接的飞书自建应用，
App ID 从 Connector 返回的已验证 `providerAccountId` 获取，租户通过该应用的 proxy 查询。
不允许手填 App ID，也不以管理员勾选确认代替应用身份验证。旧 Connector 未提供该字段时拒绝创建。

创建界面分为选择应用、配置回调两步；保存后展示回调地址与验证状态。回调已验证和已收到业务事件分别显示。
Flow 只选择事件源、事件类型及资源条件；应用 Connection binding 随事件源选择在同一次 Draft 保存中写入。
Flow 配置内可通过弹窗创建事件源，团队范围取自服务端解析的当前 Flow。创建后自动关联并展示回调地址；关联失败可重试，不重复创建事件源。
设置页继续负责完整管理，弹窗与设置页复用创建表单和接入指引。
接入顺序为创建飞书应用、连接 Connector、创建事件源、将回调地址填回飞书；事件类型仍须在飞书后台手动配置。
接入指引支持复制公网回调地址及手动检查回调验证结果，明确区分已创建、回调已验证与已收到业务事件。
资源订阅清理权仍需独立确认，放在高级资源订阅管理中，不与应用身份确认混用。

用户授权连接用于 Action 或明确要求用户身份的资源操作，不再作为可互换的应用事件入口。
需要用户身份的订阅仍须实现同一应用的可信关联后才能支持，不能把通用事件目录视为这些订阅已全部支持。

Connector 的最小修改是在运行时连接信息中公开非秘密的 `providerAccountId`，与管理接口使用同一身份来源。
部署此功能前须先更新 Connector；飞书回调接收、验签、持久化和共享订阅仍由 Open Flow Server 负责。

## 1. 目标与范围

尽可能接入飞书开放平台可用于启动 Flow 的事件，覆盖消息与群组、云文档、多维表格、日历、审批、
通讯录、任务等业务，并通过事件清单追踪其他领域。覆盖范围以官方协议、应用类型、身份和权限的核实结果为准，
不能把列出的业务分类或通用 JSON 接收能力直接视为完整支持。

采用 HTTP 事件接收方式：Open Flow Server 管理应用事件入口、持久事件接收和共享资源订阅；调用飞书
订阅、退订及资源读取 API 继续使用现有 Connector proxy。App Secret 和 access token 保持在 Connector 中。

默认修改本仓库，不预设修改 `connect`。若可信身份关联或权限验证无法通过现有接口完成，先记录具体缺失字段、
现有 API 的验证结果和最小合同补充方案，再确定跨仓库工作。缺失身份能力时不能通过跳过授权检查交付。

本次计划涵盖生产定义、Server、公开合同、Workbench 配置、相关 Lab stories、CLI/MCP 消费者、测试和接入文档。
本轮仅编写计划；真实飞书应用配置、生产订阅创建、部署和代码实施均尚未执行。

## 2. 已确认的基础与待核实协议

### 2.1 已确认的代码基础

- 公共 Trigger 定义位于 `packages/open-flow/src/trigger/`，已有 Poll、Integration 和 listener 合同。
- Provider 注册入口为 `packages/open-flow/src/trigger/providers/definitions.ts`。
- Server 已有 Integration transport/runtime/store、发布候选准备和统一监听运行时。
- 当前 Integration endpoint 和 subscription state 归单个 binding/candidate 所有，不能直接表达应用级共享入口。
- `connect` 的 `feishu` proxy 使用用户身份；`feishu_app_bot` proxy 使用应用身份，两者均可代理飞书 API。
- Server 的部署设置已有秘密写入、读取脱敏和配置版本机制，但现有数据库存储不等于独立加密保险库。

### 2.2 第一阶段必须产出的事件能力清单

逐项记录官方事件名称与版本、官方链接、应用类型、订阅身份、所需权限、事件数据范围、配置方式、
资源订阅与退订接口、续期规则、事件身份、重投行为、同步响应要求和恢复能力。

| 领域             | 核实重点                                                               |
| ---------------- | ---------------------------------------------------------------------- |
| 消息与群组       | 收消息、群及成员变化等事件的实际权限边界，消息重投身份，机器人可见范围 |
| 云文档与多维表格 | 应用级事件配置之外的资源订阅要求，文件/表/记录范围，删除与权限变化语义 |
| 日历             | 用户与应用身份限制、订阅粒度、有效期、通知与增量读取的衔接             |
| 审批             | 审批定义的应用级订阅、实例与任务事件版本、共享退订影响                 |
| 通讯录           | 租户级数据权限、成员/部门事件、敏感字段处理                            |
| 任务及其他领域   | 官方可订阅事件、身份限制、可恢复变化与仅通知事件的区别                 |
| 卡片交互等回调   | 是否要求同步业务响应，能否仅作为通知触发；不能默认等同普通异步事件     |

每个项目标记为已验证可实施、受明确前置条件限制或暂不支持，并说明原因。首批领域完成后继续核对官方事件目录，
避免仅完成示例事件就宣称“全部接入”。旧版事件只在仍有独立必要能力时支持，不自动实现全部历史版本。

另需核实应用回调地址的数量、环境区分、设置方式，以及是否存在可公开调用的配置 API。
目前官方接入说明要求在开发者后台配置地址和事件类型，再对部分资源调用订阅 API；不能把后者当成创建独立 webhook。

## 3. 对象与模块归属

### 3.1 飞书应用事件源

在部署层建立飞书应用事件源，保存稳定 identity、App ID、环境/平台身份、事件接收配置、允许的租户和
Connector 作用域关联、配置版本及安全健康状态。事件源由部署管理员管理，独立于 Flow 的发布与删除。

每个事件源有稳定回调地址；具体路径和字段在合同设计阶段确定。公网路由标识只用于寻找事件源，不能充当认证。
需要区分飞书测试与正式环境时，依据官方实际路由和凭据作用域建立独立记录，不能把不同环境事件混入同一来源。

同一上游应用事件配置由一个部署负责管理。不能假设多个部署可独立修改同一个回调地址或自行退订共享资源。
多部署集中事件分发不属于本次实现。

### 3.2 远端资源订阅

Server 保存实际资源订阅身份、期望状态、观察到的远端状态、调用所需的固定 Connector 作用域、操作版本、
重试/续期时间，以及是否具有清理权。远端网络调用复用 Connector proxy。

订阅键按照每个飞书 API 的真实作用域构造，可能包括应用、租户、订阅用户、资源类型和资源 ID。
Connection ID 是调用凭据引用，不能无条件作为上游订阅身份；事件源记录 ID 不同也不能让同一远端资源拥有两个协调者。
对同一远端订阅的身份建立唯一约束。

### 3.3 Trigger 的订阅需求

Flow Revision 保存事件源引用、Connection binding、事件类型与业务资源筛选，不保存回调秘密和订阅运行状态。
部署保存候选发布或 current binding 对资源订阅的需求关系；通过关系判断订阅是否仍被需要，不维护第二套可漂移的引用计数。

公共包拥有业务配置、事件解析/归一化、身份提取、Provider 订阅协议和 conformance。
Server 拥有来源秘密、路由、身份授权、持久化、协调调度和 Run admission。Workbench/CLI/MCP 只消费公共合同。
不为现有所有 Provider 强制引入共享事件源；仅在真实共享行为需要时扩展现有边界。

## 4. 身份、秘密与配置

### 4.1 身份关联

发布准备必须验证事件源、Connection、Connector Team、飞书应用/租户及订阅用户之间的关联。
业务资源读取成功不自动证明该 Connection 属于配置回调的应用。

回调完成认证后，继续核对协议提供的应用、租户和用户身份，再根据已验证授权范围匹配目标。
不能仅凭相同事件类型、App ID 文本或同一接收地址把事件投递给多个 Team。
缺少可证明的用户或资源归属时，应拒绝相关监听配置或使用协议允许的权限验证，不能扩大消费范围。

关联记录需要区分部署管理员的显式授权与从可信上游获得的身份事实。阶段一确定现有 proxy 是否足够；
若不足，列出最小元数据需求，不能假设可以读取 Connector 私有凭据或依赖本地别名推断身份。

### 4.2 秘密与变更

- App Secret 和 access token 留在 Connector。
- Verification Token、Encrypt Key 保存在部署事件源记录或受支持的部署秘密配置中。
- 不复用现有 Integration 的 `callbackSecret` 代替飞书协议秘密。
- 配置 API 只写入/替换秘密，读取返回 configured 状态和版本；日志、Revision、Run input 和导出不回显秘密。
- 每次接收取得完整配置快照；使用乐观并发控制避免设置互相覆盖。
- 普通 Flow 发布不轮换验签秘密，不修改应用事件入口。
- 密钥替换需要独立接入操作；只有官方协议证明可以接受过渡密钥时才实现限时双版本，不承诺无缝轮换。
- 验签算法、解密、challenge 和时间校验按官方事件版本实现并测试，不能把普通投递校验机械套到地址验证请求上。

沿用现有部署数据库及备份的信任边界，并在运维文档写明。若需要数据库外主密钥加密，应统一评估全部部署秘密，
不在飞书代码内建立私有秘密管理框架。

存在发布需求的事件源不允许直接删除；停用来源阻断新准入并显示受影响范围，恢复时沿用既有身份和去重事实。
应用/环境身份改变应建立新的事件源并重新绑定，不能把既有 source ID 指向另一个应用。

## 5. 发布与共享订阅生命周期

| 操作                   | 需求与准入                                   | 远端订阅                                     |
| ---------------------- | -------------------------------------------- | -------------------------------------------- |
| 编辑/保存 Draft        | 不创建生产需求                               | 不发起订阅                                   |
| 发布准备               | 建立候选需求，候选不可创建 Run               | 创建或复用订阅，完成身份/权限/readiness 检查 |
| 发布成功               | 在移动 Live 的同一事务激活新需求并释放旧需求 | 持久安排无需求资源清理                       |
| 发布失败               | 释放候选需求，旧 Live 和需求保持不变         | 仅清理候选独占且有清理权的资源               |
| 暂停 Trigger/停用 Flow | 保留需求，阻断新 Run 准入                    | 保持订阅，避免反复订阅退订                   |
| 修改监听范围           | 独立准备新增需求，成功后原子切换             | 先确保新资源 Ready，再释放旧需求             |
| 删除 Trigger/Flow      | 释放相应需求并终止旧目标未准入工作           | 最后一个需求释放后清理                       |
| 回滚                   | 对目标 Revision 重新执行同样的准备和激活规则 | 无条件复用旧订阅不可作为假设                 |

应用事件源的地址验证与后台配置可以在 Flow 发布前完成。没有可查询的远端就绪证据时，明确区分
“回调地址已验证”“权限检查通过”“所需事件类型已配置”与“业务事件已接收”。不以任意回调到达冒充全部事件已就绪，
也不强制要求首个真实业务事件才能发布。阶段一确定可自动验证和需管理员确认的边界。

### 5.1 订阅操作并发与恢复

按真实远端订阅键协调外部操作，复用现有持久 work、claim、取消、deadline 和维护调度机制。
外部请求在事务外执行；提交操作结果时检查版本与执行权。

退订开始后出现新需求时，新候选不能直接成为 Ready。等待退订结果确定，再根据需求重新订阅。
清理与重新订阅不并发修改同一远端资源。旧操作在租约过期后仍可能在上游完成，本地版本校验并不能撤销其副作用；
超时/崩溃后的不确定结果必须通过上游查询、可证明的幂等语义或显式失败处理，不能仅凭重新领取 lease 就认定安全。

无法查明当前状态、无法安全重试的 Provider 操作进入可恢复的诊断状态，阻止依赖该资源的新发布。
重试退订失败不能影响仍有需求的其他订阅，也不能撤销已成功的 Publication。

### 5.2 远端清理权

本地零需求不代表其他系统不再使用该订阅。只对明确由当前部署接管管理的资源自动退订。
订阅 API 幂等返回成功不构成“本次创建了独占订阅”的证据。

应用配置流程明确管理归属；发现已有订阅但无法证明清理权时保留资源并报告，禁止隐式接管。
操作人员可在独立配置流程显式接管已有订阅，不在每次 Flow 发布时重复确认。

## 6. 事件接收、分发与语义

### 6.1 持久接收

回调先完成大小限制、认证、解密和结构校验。地址验证等同步协议请求立即按协议响应，不生成业务事件。
普通事件在一个本地事务中写入去重后的事件及接收时匹配的有效目标，再响应成功。
持久化失败或达到接收容量上限时返回协议允许的失败，不先确认后丢弃。

事件记录仅保存协议与投递必需的数据，清除 token、认证字段和无关请求头，不记录完整原始请求日志。
共享原始事件不通过任意 Flow 的读取接口暴露。分发工作复用 Server 维护运行时，不引入外部消息中间件。

### 6.2 目标、去重与准入

- 接收事务固定目标 binding 的语义身份及当时有效的发布信息；随后新发布的 Flow 不追加到旧事件目标中。
- 普通异步重投不能重新计算目标集合，否则同一上游事件会误投给后来创建的 Flow。
- 分发时检查 current binding、Live、运行状态与必要授权；旧 worker 不得跨版本提交。
- 每个目标的 Run admission、投递完成和目标去重事实在同一权威事务提交。
- 一个目标容量不足只重试该目标，不能阻塞其他目标，也不能重复执行已经准入的目标。
- 发布切换前尚未准入的旧目标按既有 authority 规则终止，不把它悄悄移交新语义；记录可解释的跳过原因。
- 事件去重键按版本和事件类型定义，区分 delivery identity、业务事件 identity 与资源 identity。
  不用文档/消息对象 ID 去重所有变化，不假设所有事件都能仅用 `header.event_id`。

明确去重保留期、最大接收体积、积压容量和已完成记录保留策略，数值根据飞书重投上限与现有部署约束核实后确定。
待投递历史事件不能仅因超过普通保留期被静默清除；过期或容量处置必须成为可见的失败/缺口。

### 6.3 暂停、停用和恢复

建议事件型 Trigger 在暂停期间不创建新的目标投递；恢复后接收新事件，不承诺回放暂停期间历史。
暂停前已持久接受且尚未准入的目标保留，暂停期间不准入，恢复后仅在原 binding 仍有效时继续。
监听范围改变、删除或发布 authority 失效时按旧目标终止规则处理。

读取型 Trigger 沿用既有 checkpoint 恢复合同，不把事件型的暂停规则套到 listener/Poll 上。
只有上游确实提供增量读取时才组合通知与扫描，回调不直接推进扫描游标。
这些新增规则在实现阶段同步写入公共合同，不能从本计划推断现有 Trigger 的行为已经改变。

### 6.4 输出与事件类型

提供统一事件 envelope，包含稳定事件身份、事件类型、发生时间（协议提供时）、经校验的来源范围和业务 body。
常用事件提供确定的 payload schema 和业务配置，避免用户手写 JSON 路径才能使用。
其他已验证的普通异步事件可以由通用事件 Trigger 承载，但仍受订阅身份、权限和资源范围约束。
不默认订阅所有事件；每个 Flow 明确选择所需范围。

要求同步业务决策的卡片/其他回调单独核实合同。无法通过普通 Run 及时完成响应的能力明确列为限制，
不能先返回成功再声称完整支持该交互。普通事件监听也不附带自动回复或发送消息副作用。

## 7. 实施阶段与退出条件

### 阶段一：协议和身份验证

- 完成事件能力清单与官方链接，核实应用入口、身份、资源订阅和事件重投协议。
- 通过现有 proxy 验证用户/应用身份所需的只读信息与订阅接口合同；真实外部写入使用明确的测试资源范围。
- 确定来源与 Connection 的可信关联方法、远端订阅唯一键和清理权规则。
- 明确 readiness 的自动检查能力与人工配置前置条件。

退出条件：至少消息类和一种有资源订阅的事件可以给出完整且可验证的身份、准备、接收和清理链路。
如需 Connector 补充，先给出具体最小变更，不扩大为事件接收平台改造。

### 阶段二：公共合同与部署事件源

- 确定事件源引用、配置/状态 API、Provider 协议扩展及部署能力声明。
- 实现部署来源记录、秘密写入/读取脱敏、权限检查、稳定路由与握手。
- 添加显式数据库迁移，保留现有 Integration/Poll 数据和 endpoint 行为。
- 更新 API 解码、Revision 校验和相关 CLI/MCP 消费者；未配置来源的合法 Draft 可以保存，发布诊断准确定位。

退出条件：来源可配置并验证地址；伪造、跨租户、错误应用、错误密钥和不合法输入均不能进入业务接收。

### 阶段三：持久收件与多 Flow 最小闭环

- 用一种已核实消息事件实现真实 Provider 定义、接收、目标固定、去重和异步 Run admission。
- 实现积压、重试、容量与清理策略，接入维护调度和安全健康诊断。
- 验证同一来源两个 Flow 的独立消费及跨 Team 隔离。

退出条件：重投、崩溃恢复和单个 Flow 背压下，每个有效目标最多准入一个 Run；后来发布的 Flow 不接收旧事件。

### 阶段四：共享资源订阅与发布事务

- 选择阶段一验证通过的资源事件，实现需求关系、共享订阅协调、准备/激活/释放及清理权。
- 集成 publish operation 和最终 Live 事务，不绕过当前 PublicationStore 权威边界。
- 处理退订与新发布并发、超时结果不确定、失效 Connection、删除与清理恢复。

退出条件：两个 Flow 共用订阅，删除其中一个不退订；发布失败不影响旧 Live；清理与新发布并发时不错误 Ready。

### 阶段五：事件覆盖与产品配置

- 根据能力清单逐类接入全部已验证可支持的事件，提供常用配置与经过验证的通用异步事件入口。
- 增加资源选择 options、身份选择、来源/权限/readiness 诊断和本地化。
- Workbench 展示来源配置、受影响 Flow、连接失效和接收状态；不向用户暴露无助于决策的内部队列字段。
- 按 frontend-ui skill 维护真实组件的 Lab stories，集中展示未配置、待验证、正常、权限不足、暂停和失败状态。
- 依据真实集成范围同步 CLI/MCP 与文档，不只完成 Workbench 接线。

退出条件：能力清单每项都有实现与验证证据或具体阻塞原因，目录不存在已展示却无法配置的虚假支持。

### 阶段六：端到端验证与交付

- 在明确授权的测试应用和测试资源上完成真实握手、接收、共享订阅与退订验证。
- 完成迁移、恢复、授权隔离及既有 Trigger 回归；完成相关 Lab 视觉和必要产品集成验证。
- 更新架构事实、公开 API 合同、飞书接入说明、部署运维及能力限制。
- 停止临时验证服务器，清理本次创建的测试订阅，确认未触碰已有外部订阅。

退出条件：下方验收矩阵通过；无法完成的外部验证明确报告，不将 mock 测试等同生产联调。

## 8. 验收矩阵

| 类别       | 必须验证的行为                                                           |
| ---------- | ------------------------------------------------------------------------ |
| 协议       | 明文/加密模式、challenge、版本解析、错误签名、错误 token、畸形和超大输入 |
| 授权       | 应用/租户/用户身份不匹配、跨 Team、关联伪造、权限撤销均不能扩大消费范围  |
| 秘密       | API/日志/Revision/Run/导出不泄露来源秘密，配置并发更新不覆盖             |
| 接收       | 入库失败不成功确认；重复事件不增加目标；接收与发布切换有确定事务顺序     |
| 分发       | 一个目标背压不阻塞其他目标；准入后崩溃不会重建 Run；旧版本目标不能提交   |
| 共享订阅   | 两个消费者只需要一份真实订阅；删除一个不退订；未知归属资源不自动清理     |
| 发布       | 候选不准入；失败保留旧 Live；新增/移除需求与 Live 原子切换               |
| 并发       | 退订中新需求、lease 过期、请求超时后迟到成功、重启后恢复均不误判 Ready   |
| 暂停与删除 | 暂停期不建立新事件目标，既有投递按合同保留；删除和失效目标可终止并清理   |
| 恢复       | 事件/投递/订阅状态跨重启恢复，去重窗口明确，不能恢复的历史缺口可见       |
| 回归       | Manual/Webhook/Cron/Poll/既有 Integration 行为和数据不被共享来源改造改变 |
| 产品       | 配置状态清晰，错误可定位可恢复，真实组件 Lab 状态与实际使用流程一致      |

迭代阶段运行行为对应的聚焦测试；最终运行仓库规定的检查。任何 Git commit 前必须从根目录执行并通过
`bun run check`。本计划的提交若需要 commit，也遵循同一要求。

## 9. 文档落点与范围控制

- `docs/architecture.md`：实施后的来源 owner、共享订阅和持久接收事实。
- `docs/control/contracts/control-api.md`：公开字段、路由、错误和消费者合同。
- `docs/feishu-triggers.md`：实施时新增，记录应用配置步骤、事件清单、权限、暂停及恢复保证。
- Server 部署文档：回调公网配置、秘密信任边界、容量、备份恢复及运维处置。
- 本计划：保留阶段进度、验证结果和设计取舍，不替代当前权威合同。

不引入外部队列、通用事件总线、长连接常驻客户端、独立秘密管理框架或所有 Provider 的统一重构。
如果协议证据要求改变上述边界，应先记录具体不成立的假设及影响，再调整实施方案。
