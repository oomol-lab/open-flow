# Agent 节点规格草案

状态：实施中，模型、Scheduler、Server 与客户端主链路已接通，正在完成验收。2026-09-08。

本文定义首版 Agent 节点的产品行为、执行边界与验收要求。范围选择是本草案的提议；精确序列化字段、错误码和协议版本在底层合同阶段写入技术参考。本文不声明现有产品已经支持这些行为。

产品边界依据：[现有架构](../architecture.md)。

选型依据：2026-09-07 的 pi 与 Mastra 对比实验支持选择 Mastra，以减少 Agent 审批快照、待审调用处理和工具结果续接的自建工作。Run 执行权、并发恢复保护、Scheduler 暂停合同及外部动作结果不确定性的处理仍由 Open Flow 宿主负责，框架快照不成为第二套 Run 权威状态。实验使用确定性模型 fixture，只验证执行语义，不代替真实模型或产品集成验收。

## 1. 目标与首版范围

用户可以在 Flow 中配置一个 Agent，让模型根据任务调用明确允许的 Connector 工具，对选定工具的具体调用请求人工审批，并在同一 Run 内恢复执行，最后提交可供下游消费的结果。

首版必须包含：

- 显式任务输入、System Message、模型选择和最大模型调用轮数。
- Connector Action 工具，支持固定参数、节点输入绑定参数和模型生成参数。
- 同一工具的多次独立调用，以及同一模型响应中的多个工具调用。
- 工具输入校验、普通工具错误反馈、取消、deadline 和执行结果不明的处理。
- 对指定工具的每次调用审批；支持同一模型响应中多个待审调用分别批准或拒绝。
- Agent 节点内部持久化暂停、进程重启后恢复、重复决议和并发恢复保护。
- 文本或结构化最终输出，以及工具调用和审批过程的运行记录。
- Server、Control API、Workbench 与 Command 的完整创建、运行、查看和决议闭环。

首版不包含跨 Run 聊天 Memory、自动上下文压缩、动态工具发现、模型自行选择账号、Subflow as Tool、Agent as Tool、MCP 工具接入、模型自动 fallback 和独立聊天产品。普通 LLM Task 继续服务单次生成场景。

首版 Agent 仅允许放在根 Flow 图内。Subflow 中的 Agent 在 validation 阶段明确拒绝，避免在尚无嵌套暂停合同的情况下运行到中途才失败。现有普通 Subflow 行为不变。

## 2. 用户场景

作者配置“处理客户请求”Agent，允许查询客户资料和发送邮件。查询不需要审批，发送邮件的每次调用需要审批。发件账号与收件人固定，主题和正文由模型生成。

```text
Trigger → 读取客户请求 → Agent → 保存处理结果

Agent 内部：
查询客户 → 生成邮件调用 → 暂停并审批
                         ├─ 批准：执行原邮件调用 → 模型继续
                         └─ 拒绝：将拒绝交回模型 → 模型继续
最终结果通过校验 → Agent 完成 → 保存处理结果
```

等待期间没有发送邮件，也没有启动“保存处理结果”。重启或修改 Draft 后批准，仍执行原 Run 固定 Revision 下的原调用。拒绝本次邮件不自动判定整个任务失败，Agent 可以解释无法执行的原因并返回结果。

Workbench 添加工具时明确选择“自动执行”或“执行前确认”，不根据动作名称猜测读写性质。当前动作目录不提供风险分类，因此两项均不预选。新增工具的参数默认由 Agent 根据任务填写，添加前向用户说明；作者可在高级参数设置中固定值或绑定节点输入。已有工具的审批策略与参数来源保持不变。默认视图展示账号、执行方式和已指定参数摘要，完整参数编辑按需展开。

## 3. 配置与 Revision

Agent 是具有独立产品语义的任务配置。具体 Node/Task 序列化形式沿用现有模型确定，不把 Agent 伪装成包含私有控制字段的普通 LLM 输出。

Revision 必须固定任务说明、System Message、模型选择、工具声明、工具参数来源、审批策略、可选审批通知、轮数上限与最终输出声明。布局不参与这些语义。模型 credential、Connector credential、审批 capability 和运行快照不进入 Revision。

审批通知按 Agent 配置，该 Agent 下所有需要审批的工具共用一份通知声明。通知可选；未配置时，Operator 通过 Workbench 或 Control API/Command 决议。配置时复用现有 Wait notification 的 Connector Action、Connection、输入和消息字段合同，收件等输入由作者固定或绑定此次节点输入，不能由模型生成或修改。通知能力进入 Run/Publish eligibility 检查，不能借业务工具的授权隐式获得通知权限。

宿主为每个当前等待生成工具、账号、完整业务参数及决议链接的审批消息，填入声明的通知消息字段。只通知当前可决议等待，排队中的其他调用不提前生成可用决议链接。未配置通知时不创建通知 work；通知失败仍保留管理入口。

任务说明可以引用已解析的节点输入。节点输入来源继续遵守祖先可达性和保证完成规则，不允许模型或 adapter 任意读取其他节点结果。

Run admission 固定 Revision、closure、Variable、模型部署配置及现有 Flow scope。恢复不能采用新 Draft、新 Variable 值或新模型配置。外部授权有效性仍需在具体调用时检查；账号撤权时明确失败，不能换账号继续。

确定性 validation 负责配置形状、参数来源、输出声明与图约束。部署 eligibility 负责模型和 Connector capability 是否配置、绑定资源是否有效，不把外部探测放入 Revision validation。

## 4. 工具合同

### 4.1 工具身份与授权

每个工具声明固定一个 Action 与一个 Connection；无需认证的 Action 不要求 Connection。同一 Action 使用不同账号时声明为不同工具。首版不把 Connection 选择暴露给模型。

工具有稳定的声明身份和供模型理解的名称、说明。模型名称在当前 Agent 工具集合内唯一，不能取代 Action、Connection 或调用身份作为授权依据。名称约束与到 provider 工具名的映射在技术参考中规定，不能静默覆盖冲突。

工具调用复用现有 Connector host、Run 固定 scope 和能力校验。宿主检查声明、参数、当前 invocation 与 Run 状态；未知工具和已失效能力不能进入业务实现。

每次模型请求的业务调用获得独立宿主调用身份，即使参数相同也不自动合并。传输重投或批准后续接同一次调用时保留该身份。provider 的 tool-call ID 用于消息关联，不单独作为跨 Run 的权威身份。

### 4.2 参数来源

每个工具参数只允许一个来源：

| 来源     | 行为                                          |
| -------- | --------------------------------------------- |
| 固定值   | 作者在 Revision 中声明                        |
| 节点输入 | 从此次 Agent invocation 的固定输入解析        |
| 模型生成 | 将字段类型、必填性与说明暴露为模型工具 schema |

模型只获得需要生成的字段 schema。宿主拒绝模型提交未声明字段或覆盖固定字段的请求；不通过对象覆盖顺序决定权限。

参数使用公共层可确定性解码的 schema 子集，复用现有类型能力。缺失必填值、类型不符或不支持的 schema 必须明确拒绝，不静默降级。工具 schema 及其参数来源参与 Revision，不能在恢复时从可变目录重新推导。

宿主合并并校验完整业务参数后才能创建可审批调用。审批固定这份完整参数；批准后不得重新求值输入表达式或让模型重新生成参数。调用时仍需校验当前授权。

### 4.3 调用次序、结果和错误

首版按模型响应中的调用顺序串行处理工具，不增加工具并发选项。工具次数与模型轮数分别记录；一轮可以请求多个工具。

同批所有工具调用均产生成功、普通错误或拒绝结果后，才发起下一次模型请求。多个待审调用逐项决议；批准第一项后执行该项并保存结果，再等待下一项，不在两项之间重新请求模型。

错误按执行事实分类，不能仅凭 HTTP 状态或本地异常类型判断能否让模型继续：

| 情况                                                             | 行为                                                         |
| ---------------------------------------------------------------- | ------------------------------------------------------------ |
| 执行前参数不合法                                                 | 业务实现不执行，将参数错误交回模型，允许修正后发起新调用     |
| 明确未成功且未产生副作用的业务错误                               | 将普通工具错误交回模型，允许模型决定下一步                   |
| 已确认执行成功或产生部分副作用，但响应解码、序列化或结果处理失败 | 记录已知执行事实，终止 Agent，不作为可修正的普通失败交回模型 |
| 请求已发出，无法确认是否成功或产生副作用                         | 结束为不确定失败，不自动重试，也不交回模型继续调用           |

宿主授权失效、取消、deadline 与资源限制保持终止语义。外部请求超时、连接断开、非法响应或响应超限若无法证明业务未执行，不能归类为普通业务错误；若同时无法确认副作用状态，记录不确定失败。分类依据来自 Connector/provider 的明确合同和实际执行证据，不能让模型猜测。

工具响应作为数据进入模型上下文，不授予额外能力。首版对响应超限、不可序列化和解码失败终止执行，不静默裁剪或丢字段后继续。工具一旦发生终止类错误，当前批次剩余工具不执行，也不再发起模型请求；已发生的副作用不回滚。具体上限与错误码在技术合同阶段固定。

大结果使用独立 Run 结果存储和按需读取，不因超过模型预览预算而失败。具体行为见 [Agent 大工具结果处理](2026-09-08-agent-results-spec.md)。

## 5. 模型循环与最终输出

每次发起模型请求前检查剩余轮数、Run 执行预算和已配置的节点执行预算。已发起的请求消耗一轮，失败或暂停不能返还轮数；恢复不会重置计数。审批、工具执行和拒绝反馈本身不消耗模型轮数。

最后允许的一轮如产生工具调用，可以完成这些调用；若仍需下一轮模型生成最终答案，则因轮数耗尽而失败。不得将最后一个工具结果冒充 Agent 最终答案。

首版不自动重跑整个 Agent，也不在 provider 失败后切换模型。provider adapter 的传输行为必须与请求取消、计数和可能已执行的工具相容。

最终输出支持文本和按声明约束的 JSON。完整输出通过类型与可序列化性校验后，按既有节点完成合同一次性提交。结构化输出不合法时明确失败，首版不增加隐式模型修复循环。

流式模型响应必须在实际 provider 接入中验证，包括分片工具名、参数与多个调用的组装。完整工具调用解析和校验前不执行工具。文本片段或进度只供观察，不能作为最终 output 触发下游；首版不要求浏览器断线后续传每个 token。

provider 要求保留的消息块、签名和工具结果关联由 adapter 正确保存与续接，不能仅持久化可见文本。恢复格式带版本身份；不支持的格式明确失败，不丢字段后猜测性恢复。

### 5.1 节点超时与执行预算

Agent 支持节点既有的可选 `timeoutMs`，其值随 Revision 固定，限制同一次节点 invocation 各执行阶段累计的实际经过时间。未配置时不增加独立节点上限，仍受 Run 总预算约束。节点预算由公共 Scheduler 计量，Run owner 持久化；不能由模型或框架消息决定剩余时长。

每段计时从 Scheduler 开始或恢复该节点执行时启动，覆盖 adapter 恢复、模型与工具请求的异步等待、结果处理以及生成可恢复暂停数据的时间；到 Scheduler 接受有效暂停结果并收回执行权，或节点结束时停止。提出审批意图本身不停止计时，尚未结束的请求也不能被算作人工等待。

节点已暂停后，等待兄弟节点收敛、人工审批、审批队列中其他 Agent 的执行，以及决议后等待领取执行权的时间，都不消耗该节点预算。多个 Agent 同时运行时各自计时，暂停后互不扣减。Run 总预算仍按既有 Run/Wait 合同独立计量，不能把节点预算相加作为 Run 用时。

每次暂停保存扣除本段用时后的剩余节点预算，恢复前校验并继承；不重新分配完整 `timeoutMs`，也不采用包含人工等待时间的绝对截止时间。配置了节点超时却缺失或损坏剩余预算的 checkpoint 必须 fail closed，不能退回原始上限。进程重启不能返还已消耗预算，运行中崩溃仍遵守第 6.4 节的恢复决策。

Run 或节点执行预算任一耗尽，都沿既有取消与失败传播终止执行，不再启动模型或工具调用，也不发布新的审批等待。模型、工具异步等待期间同样执行超时约束，不能只在发起请求前检查。超时与暂停竞争时，仅剩余预算为正的有效暂停结果可以进入 waiting。Wait 的到期时间独立限制已激活审批的等待时长，不替代节点执行预算。

## 6. 持久化暂停与审批

### 6.1 暂停边界

节点执行合同必须区分完成、失败与可持久化暂停。暂停携带框架私有 continuation 或可恢复引用，以及宿主可检查的待审调用事实。暂停不构成节点完成。

continuation 至少能恢复模型消息、当前批次、已处理工具结果、未处理调用和剩余轮数。宿主同时固定 Run、Revision、节点、invocation、调用、等待身份、完整待审参数与审批策略，并在 Scheduler checkpoint 中保存每个未完成 Agent 已配置的剩余节点预算，不能让框架快照成为第二个 Run 状态机。

创建等待前，所有恢复所需数据必须已可靠保存。若快照在框架 store、等待在 Run store，必须规定提交顺序和失败恢复：允许清理未引用快照，不允许发布引用尚不存在快照的 waiting 状态。持久化失败时不通知审批人、不执行待审工具、不从节点开头重试。

Run owner 在同一权威事务中提交包含各节点剩余预算的 Scheduler checkpoint、continuation 引用及完整性身份、当前等待、Run 剩余执行预算和已配置的通知 work，并将 Run 置为 waiting。通知在事务外按现有 Wait 通知合同发送。

等待期间释放 Executor session 和同 Flow 执行槽。恢复继续同一 Run 与同一节点执行身份，保持已完成节点结果、跳过状态、启动输入和 Variable 快照。

### 6.2 并行分支

首个节点提出暂停后，Scheduler 停止启动新节点，并等待已经运行的兄弟节点完成或提出可保存的暂停。兄弟节点失败时按既有失败传播结束 Run，不把不完整状态发布为 waiting。

多个已运行 Agent 可以同时提出暂停。checkpoint 必须保留所有未完成节点的 continuation 和待审队列，不能用最后一次暂停覆盖前一次。普通图 Wait 与 Agent 待审可以被同一 checkpoint 保留。

一个 Run 同一时刻只暴露一个可决议的等待，复用现有 first-writer-wins 决议模型。初次收敛时，各暂停节点只将当前阻塞它的一个等待入队，按稳定 nodeId 的字典序排列，不按 title、画布位置或回调到达顺序排列。Agent 同批次中尚未轮到的工具保存在自己的 continuation 内，不提前加入全局等待队列。

决议后仅恢复该队首节点。批准时执行原调用并保存结果，拒绝时保存拒绝结果，然后依第 4.3 节继续处理该 Agent，直到下一次需要审批、节点完成或发生终止类错误。期间允许执行不需审批的工具；只有当前批次结果齐全才可继续模型请求。不要求 adapter 在每个普通工具返回后提供额外暂停点。

该 Agent 再次遇到审批时，将新的等待加入现有队列尾部，即使其 nodeId 排在其他节点之前也不插队。它完成时提交最终输出并移出暂停集合；发生终止类错误时按既有失败传播终止 Run。普通图 Wait 决议后提交所选 action 的结果，并移出等待队列。

例如初次队列为 A1、B1，批准 A1 后 A 在同批下一工具或后续模型响应中提出 A2，下一队列必须为 B1、A2。若 A 直接完成，则下一项仍为 B1。当前模型批次尚有待审工具时，切换到 B 不得导致 A 提前发起下一次模型请求。

队列仍非空时，保存更新后的全部 continuation、各节点剩余预算、已完成结果和队列，激活队首等待，不启动新的普通图节点。待审队列清空且恢复节点已完成后，才恢复常规图调度。Run 或当前节点执行预算耗尽时直接失败；模型轮数耗尽仅阻止下一次模型请求，当前批次工具及其审批仍按第 5 节处理。切换等待不重置任何预算。

等待到队首并原子发布为 waiting 时，按现有 Wait 时长合同生成到期时间；尚未激活的队列项不发送通知、不接受决议。已激活等待的到期时间不能因通知重试或进程重启延长。队列与激活规则由公共 Scheduler 和 Run owner 实现，客户端不能维护另一份队列。

### 6.3 审批内容与决议

审批展示目标 Action、实际账号标识、完整业务参数、所属 Flow/Run/节点与本次调用身份。模型提供的解释只能作辅助信息，不能替代待执行参数。凭据值不展示；业务参数按现有用户数据与权限边界处理。

批准只授权原调用及其固定参数。拒绝只阻止本次调用，并产生拒绝工具结果；不自动撤销该工具权限或终止 Run。后续模型若再次提出同类调用，必须创建新调用并重新审批，仍受轮数和预算约束。

首版只提供 approve/reject，不在审批界面编辑参数。审批策略按工具固定，不能由模型选择是否需要审批。未知决议、错误等待身份及参数不匹配必须拒绝。

所有决议入口共享现有 Run owner。Control API 对已决议等待沿用既有返回合同：HTTP 200，返回胜出的 action 和原 resolvedAt；请求与胜出 action 相同则 `resolutionAccepted: true`，相反则为 `false`。该值表示请求是否与已接受决议一致，不表示本次又启动了一次执行。两种重投都不改变 Run 状态、不新增决议事件、不执行工具。

每个已决议等待保留独立 receipt，至少包含 Run/Wait/节点/调用身份、允许 action、胜出 action 与决议时间；普通图 Wait 无工具调用身份。receipt 在进入下一等待后和 Run terminal 后仍保留，随所属 Flow 的物理删除清理，不受 RunEvent 明细 retention 影响。首次决议及其 receipt 必须原子提交；创建下一等待不能覆盖旧 receipt。该要求统一适用于本 spec 扩展后的普通 Wait 与 Agent 审批。

旧决议请求按原 waitId 查 receipt，不能使用当前等待的 action、参数或策略解释。未经决议即被取消或到期的等待不伪造批准/拒绝事实，旧请求按既有不可决议行为返回，不再排队执行。不存在的等待仍返回既有 not-found。

外部通知 capability 仍只绑定原等待，继续校验其身份和有效期；保存 receipt 不延长链接有效期，也不使旧链接获得下一等待的权限。有效的外部重投与管理入口读取同一决议事实。通知失败不自动决议，Operator 仍可通过现有管理入口处理等待。

### 6.4 恢复、取消与结果不明

恢复请求先由 Run owner 原子领取执行权，只有领取成功者调用 adapter。批准后执行原工具、保存工具结果，再继续当前批次；恢复不能重跑已经保存结果的调用或重新生成待审参数。

进程在业务副作用落下、结果尚未可靠提交时死亡，必须在确认旧执行者已停止后结束为现有不确定失败语义。首版不自动补偿或重新执行，不承诺外部副作用 exactly-once。

取消 waiting Run 后，原审批入口与 continuation 均不得再启动工具。运行中取消沿既有 Effect 生命周期传递到模型和工具；取消、deadline、资源限制及 sibling failure 不能作为普通可恢复工具错误被模型吞掉。取消不承诺撤销已经发生的外部副作用。

取消、决议、领取、完成和崩溃恢复竞争必须由同一 Run store 收敛到唯一权威状态。节点最终输出和 Run terminal 不能重复发布。恢复不重置 Run 或节点预算；Run 暂停时间沿用现有 Wait 合同，节点计时遵守第 5.1 节。

## 7. 模块所有权与框架选择

| 层                       | 拥有的职责                                               |
| ------------------------ | -------------------------------------------------------- |
| 公共 Flow 模型           | Agent 配置、工具参数来源、静态 validation、编码与 digest |
| 公共执行合同与 Scheduler | 节点暂停、并行分支收敛、等待队列、最终输出与恢复语义     |
| 部署 Run owner           | 执行权、权威状态转换、持久化、通知、预算与崩溃决策       |
| Agent adapter            | 模型循环、provider 消息转换、工具结果续接、框架快照读写  |
| Connector host           | 绑定授权、实际外部调用、调用身份及错误语义               |
| Workbench 与 Command     | 编辑、观察和决议，消费公共合同                           |

首个 adapter 暂以 Mastra 为候选，依据是 POC 已验证的原生审批恢复与多调用决议收益。选型在真实模型、正式 Scheduler 和故障矩阵通过后落定；不以 bundle 大小推导总体维护成本。

产品 Revision、Control API 与公共暂停合同不包含 Mastra/pi 专有消息格式。框架快照保持部署私有且可检查版本与完整性。首版只实现一个 adapter，不建设双框架切换或通用插件系统。

公共合同须保持 common/browser/node 所有权和跨部署可移植性。本仓库 Server 是首个正式交付目标；本地 workerd 验证不能被表述为线上 Cloudflare 部署通过。

## 8. 编辑与运行观察

Workbench 提供任务、模型、工具及参数来源、审批、可选通知和输出配置。工具配置不创建普通执行边，不允许借工具引用绕过祖先输入规则。无效配置可保存在 Draft，但必须可定位、可修复，且阻止 Run/Publish。

运行视图展示 Agent 当前状态、模型轮数、工具调用身份与参数、执行结果、审批决议和最终输出。等待与工具调用关联到同一节点，恢复不会显示为新 Run。中间记录是观察投影，不能作为调度或恢复的权威来源。

复用现有 RunEvent 与 Run 读取通道，按需要扩展公共事件技术合同；不建立第二条持久化运行日志系统。框架原始快照和 credential 不进入公开事件。事件明细的 retention 与 Run terminal 保留沿用现有合同。

Command、Control API 与 Workbench 必须能表达等价配置、读取同一等待并执行同一决议。审批数据和状态由服务端生成，客户端不能根据本地模型消息猜测待审动作。

## 9. 必须通过的验收场景

| 场景                                                 | 验收结果                                                                         |
| ---------------------------------------------------- | -------------------------------------------------------------------------------- |
| 查询 → 计算结果 → 最终输出                           | 工具结果进入下一轮，最终输出只提交一次                                           |
| 固定参数与模型参数混合                               | 固定值不被覆盖，完整参数在宿主入口校验                                           |
| 未知工具、未授权账号、非法参数                       | 业务实现未执行，错误按合同反馈                                                   |
| 同一工具与相同参数调用两次                           | 两次独立身份，不因参数相同被错误去重                                             |
| 一轮多个普通工具                                     | 按顺序执行，结果齐全后只继续一次模型请求                                         |
| 审批前退出，重启后批准                               | 待审工具此前未执行；只执行原调用，不重跑查询                                     |
| 审批后拒绝                                           | 不执行该工具，模型收到拒绝结果                                                   |
| 双待审，分别批准和拒绝，阶段间重启                   | 保存已处理结果，不提前请求模型、不丢待审调用                                     |
| 读取与写入混合批次、其中一项普通失败                 | 每项结果可识别，已完成副作用不重放                                               |
| 写入成功后响应超过资源上限、非法或不可序列化         | Agent 终止，无第二次调用，无后续工具或模型请求；无法确认副作用状态时是不确定失败 |
| 重复及相反决议、两个实例并发恢复                     | 只有一个决议事实与一个执行者                                                     |
| 第二项 waiting 时及 Run terminal 后重投第一项决议    | HTTP 200 返回第一项胜出事实与正确 resolutionAccepted，不改变当前等待或启动执行   |
| 决议事件已按 retention 清理后重投                    | receipt 仍可返回原事实，不依赖事件重建；Flow 物理删除后不可查询                  |
| 副作用已发生、结果提交前进程崩溃                     | 不自动重放，结束为不确定失败                                                     |
| 快照写失败、引用缺失、损坏或版本不支持               | 不发送可用审批、不执行工具、不从头猜测恢复                                       |
| 等待中修改 Draft、Variable、目录说明                 | 原 Run 参数和合同保持固定；撤权仍被实际调用检查                                  |
| Agent 与普通兄弟节点并行                             | 暂停前收敛活跃执行，兄弟结果保留，下游不提前运行                                 |
| 两个 Agent 同时暂停，或 Agent 与图 Wait 并存         | 所有 continuation 保留，等待顺序稳定，逐项恢复                                   |
| A1、B1 已排队，A1 决议后产生 A2，再次重启            | 次序为 A1、B1、A2；同批待审未处理完时 A 不提前调用模型                           |
| 排队等待激活、通知重试与进程重启                     | 仅队首可决议，激活时开始计到期时间，重试和重启不延长有效期                       |
| 等待或执行中取消，与决议/完成竞争                    | 唯一终态，后续调用被阻止，旧能力失效                                             |
| 轮数和总预算耗尽，期间有多次重启                     | 计数不重置，不以工具结果冒充最终输出                                             |
| 节点上限 10 秒，审批前执行 6 秒，恢复后仍需执行 6 秒 | 恢复时只剩 4 秒；累计到上限即终止，不完成余下调用或发布最终输出                  |
| 审批等待长于节点 timeoutMs，但未超过 Wait 有效期     | 等待不扣节点预算，批准后继承暂停时剩余值                                         |
| A 暂停后等待 B 执行及审批，队列期间重启              | A 预算不因 B 的用时减少，A/B 恢复均不重置各自已消耗预算                          |
| 模型或工具请求仍未返回时节点预算耗尽                 | 超时传播到请求并终止节点，不等响应返回才检查，不产生后续调用                     |
| 节点超时与暂停竞争，或剩余节点预算缺失/损坏          | 不发布超预算或不可验证的 waiting，不恢复为完整 timeoutMs                         |
| 真实 provider 的流式并行工具消息与签名               | 正确组装、持久化、恢复，无非法协议续接                                           |
| 结构化最终输出非法                                   | 整体失败，下游没有部分结果                                                       |
| 控制端通知发送失败与重复投递                         | 无自动决议，既有入口可处理，重复通知不重复执行                                   |
| 未配置通知，或通知配置的绑定无效                     | 无通知时管理入口可审批；无效通知绑定阻止 admission，不静默忽略                   |
| 第二项激活后使用第一项通知链接                       | 有效期内只返回第一项事实，过期不再授权，不能决议第二项                           |
| Workbench、Command 创建并审批等价流程                | 同一 Revision 语义、等待事实与结果                                               |

确定性 fixture 用于精确验证调用次数、竞争和故障窗口；真实模型用例验证网关协议与实际工具调用闭环。两类测试分别报告，不能用真实模型偶然成功代替恢复断言，也不能用 fixture 宣称推理质量通过。

## 10. 实施顺序与完成标准

1. 公共模型与规格测试：固定配置、参数 schema、暂停结果、等待队列、身份和错误分类；必要 TypeScript 类型按仓库风格命名，用户已授权不再逐批确认。精确字段和版本写入技术参考。
2. 公共 Scheduler：实现单节点和并行节点暂停、累计节点超时及剩余预算校验、图 Wait 共存、恢复与一次性完成，先通过无部署依赖的行为测试。
3. Server 与 adapter：接入权威 Run store、快照、独立历史决议 receipt、Connector、真实模型、可选通知与取消；将当前覆盖式等待存储改为能保留原决议事实的合同实现。组合跨等待重投、并发恢复、结果处理失败和崩溃矩阵，验证 Mastra 候选。
4. Control API conformance 与客户端：底层合同完整后再实现 Workbench、Command 配置、观察和决议，不在客户端补救缺失状态。
5. 文档与交付：将已实现的持久边界更新到 architecture，将精确合同更新到技术参考；删除过时的未发布路径，不保留无需求的兼容层。

完成意味着首版范围和验收矩阵均有实现与证据，真实模型路径通过，框架选择落定，客户端可用；仅 POC 成功或配置面板完成不算交付。

实现按阶段运行相关检查，交付前运行 `bun run format`、`bun run check`、`bun run test`、`bun run build`；发布 CLI、包入口、元数据或静态 Workbench 资产变化时加跑 `bun run test:package`。不启动或自动化浏览器。
