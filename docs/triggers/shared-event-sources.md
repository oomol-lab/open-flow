# Shared provider event sources

Create an event source in the Workbench, choose its Connector Team and connection, then select that source in each Trigger. Each matching Flow receives its own delivery; upstream retries do not create another Run for an admitted event. Pausing one consumer does not remove another consumer's subscription.

| Trigger                          | Source configuration                                                                    | Supported business events and boundaries                                                                                                                                                                                                                  |
| -------------------------------- | --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `slackbot.on_event`              | Slack App ID, workspace ID, application Signing Secret and verified Bot connection      | App mentions and new user messages in Bot DMs. Bot messages, edits, other subtypes and externally shared channels are excluded. Optional channel IDs filter consumers. Reauthorize existing connections for `app_mentions:read` and `im:history`.         |
| `jira.on_issue_event`            | Jira Cloud OAuth connection and project key or numeric ID                               | Issue creation, updates and comments. One dynamic webhook per source/project; consumers select events. Requires `read:jira-work`, `read:jira-user`, `manage:jira-webhook` and the OAuth app's matching client secret in Connector.                        |
| `sentry.on_issue_alert`          | Organization ID/slug, Integration UUID, Installation UUID and Integration Client Secret | Issue Alert Rule integration actions only. Connector checks organization access and the installed integration. Optional project IDs and exact rule labels filter consumers. Raw event, issue, project and rule details remain in `body`.                  |
| `intercom.on_conversation_event` | Developer App ID, application Client Secret and verified workspace/admin connection     | Customer-created conversations, customer replies and ticket creation. Administrator replies are excluded. The notification workspace must match the connected workspace.                                                                                  |
| `zoom.on_recording_ready`        | Developer App ID, Webhook Secret Token and connected user                               | Completed cloud recordings hosted by the connected user. This is not an account-wide administrator feed. Meeting instance UUID distinguishes recurring meetings. `body` contains completed recording files; the envelope's download token is not emitted. |
| `fireflies.on_meeting_ready`     | Connected account and Webhooks V2 Signing Secret                                        | Transcription and summary completion are separate. Connector checks that the connection can read the meeting before admission. Reprocessed versions have distinct identity; delayed older versions are ignored.                                           |

Slack, Intercom, Sentry and Zoom share an application callback across installed workspaces/accounts. Configure the URL once in the upstream application. Sources for the same application must use the same signing secret. Rotating that secret invalidates application verification for all its sources; reverify after rotation. Disabling one source keeps the application callback available for other sources. Application-level settings are managed by the deployment administrator.

Fireflies has an account-source callback. Jira has a project-source callback. Flow configuration contains the source ID and business filters, never webhook secrets or remote subscription IDs. Secrets are omitted from source read responses.

## Setup and readiness

- **Slack:** enable Event Subscriptions, copy the callback URL, complete the signed URL challenge, subscribe to `app_mention` and/or `message.im`, then install or reinstall the Bot with the required scopes. The connection's Bot user and the callback's app/workspace/authorization identities must match.
- **Intercom:** configure topics and callback in Developer Hub and send a signed `ping` for the connected workspace. The existing connection must have a verified `workspace:admin` identity; an administrator-only fallback is insufficient.
- **Sentry:** make the Custom Integration available as an Issue Alert action, install it in the chosen organization, add it to an Issue Alert Rule and trigger a test alert. This signed alert verifies the source before publishing consumers. Ordinary issue-created and metric alerts are not supported by this Trigger. The two Connector backends store different account identities; the source verifies organization and installation through authenticated API reads in both cases.
- **Zoom:** enable the recording-completed subscription, configure the callback and complete signed CRC validation. Periodic CRC requests are handled without starting Runs. The connected account must be able to read its user identity and access the actual recording files; subscription and cloud-recording plan permissions still require manual verification.
- **Fireflies:** configure Webhooks V2 for transcription and/or summary, then deliver an event for a meeting the connection can read. A console test using a nonexistent meeting will not mark the source ready. Retried notifications may have a different delivery timestamp, so that timestamp is excluded from normalized business output. Deduplication uses meeting, event type and `reprocessed_at`; retention is 30 days.
- **Jira:** no manual webhook creation or secret input in Open Flow. Publish the first consumer to create the dynamic webhook. Connector keeps its ID and expiry, checks it daily and renews within seven days of expiry. The OAuth application must allow the public HTTPS callback domain. Atlassian allows five dynamic webhooks per app/user/site; additional consumers of one source share its webhook. The final consumer's removal cleans it up. Failure and expiry revoke readiness and appear in source status. Restore authorization or quota and retry publication. An uncertain creation is recovered by finding the exact callback; if it remains absent, resolve it manually before creating another source.

Jira's Bearer JWT is sent to Connector as protected callback input, separate from the authorization used to call Connector. Connector verifies it with the OAuth client owner’s secret and checks webhook ID, project and site. Invalid authentication is rejected; unavailable verification returns a retryable `503`. Callback credentials are never returned as node outputs. The implementation requires HS256 and an unexpired `exp`; validate actual Atlassian JWT claims during manual acceptance.

All source callbacks currently accept JSON up to 64 KiB. Outputs contain data actually present in the callback; use existing provider Actions for missing context and files. These limits need representative large real deliveries during acceptance.

## Manual acceptance on both Connector backends

1. Create a source with a dedicated test account and the permissions above. Read it back and verify secrets are absent. Complete the platform-specific readiness step. For Jira, publish to initiate subscription instead.
2. Create, read, locally edit and validate a Trigger through the Workbench and the public CLI/MCP authoring interface. Connect an observable downstream action. Use the provider Trigger and event-source Lab stories to inspect configuration, waiting, ready and failure states.
3. Publish two consumers for one source and another source for a different workspace/account/project. Produce each supported business event. Confirm only matching Flows run; replay the same upstream delivery and confirm no duplicate Runs. Produce another event for the same object and confirm it is delivered.
4. Test invalid signatures, wrong workspace/project/host, unavailable or revoked connections and temporary Connector failure. For Jira and Fireflies, restore the verifier and retry the original event; it must result in one Run. Never paste callback secrets or Bearer tokens into diagnostics.
5. Restart Open Flow and Connector with persistent storage, redeliver the same event, and verify identity and deduplication survive. For Fireflies, deliver reprocessed versions out of order. For Sentry, trigger the same issue again with a new event. For Zoom, use two occurrences of a recurring meeting.
6. Disable one source/consumer and ensure another remains operational. Remove consumers one at a time. For Jira, verify the last removal deletes the owned webhook, renewal advances expiry, an unsuccessful renewal removes readiness, quota exhaustion is explicit, and recovery does not create duplicates. For manually configured application callbacks, removing a Flow must not delete the application's shared subscription.
7. Rotate shared signing credentials and reverify; revoke/reinstall the upstream application and reconnect as needed. Record actual delivery IDs and Run IDs without sensitive payloads. Keep these real-service checks separate from automated mock protocol tests.

HubSpot remains intentionally absent from the Trigger catalog. Its current provider uses MCP authorization, which does not establish the native Webhook app/portal identity, object scopes or signing credentials. Complete that authorization review before implementing its conditional Trigger.
